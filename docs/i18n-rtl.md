# Арабский язык и RTL

Самый недооценённый документ в наборе. Большинство проблем с арабской версией — не в переводе, а в вёрстке, поиске, датах и рендеринге PDF.

**Правило номер один:** направление не добавляют в конце. Оно либо заложено с первого компонента, либо переписывается весь фронт.

---

## 1. Локали

```
ar  — арабский, локаль по умолчанию; текст RTL, раскладка LTR (см. §3)
en  — английский
```

- Дефолт — `ar`. Корень `/` редиректит на `/ar` (или на локаль из `Accept-Language`, если это `en`).
- URL: `/ar/courses/[slug]`, `/en/courses/[slug]`. Не поддомены — проще с cookie, CDN и сертификатами.
- Слаги курсов — **латиницей и общие для локалей** (`/ar/courses/intro-to-finance`). Арабские слаги в URL превращаются в процент-энкодинг, ломают аналитику и плохо шарятся в мессенджерах.
- `hreflang` на каждой публичной странице + `x-default`.
- Выбор локали хранится в cookie `NEXT_LOCALE` и в профиле (`users.locale`) — второе важнее, оно синхронизирует язык писем и PDF.

### Fallback

Цепочка: `запрошенная → fallback курса → en → ar`.

Ответ API всегда несёт метаданные:
```json
{ "locale": "ar", "resolvedLocale": "en", "isFallback": true }
```
Фронт при `isFallback` показывает плашку: «هذا الدرس متاح حالياً بالإنجليزية فقط». Молча подсовывать другой язык нельзя — это выглядит как баг.

## 2. Локализация интерфейса

`next-intl`, сообщения в `messages/{ar,en}.json`, плоские ключи по неймспейсам:

```json
{
  "course": {
    "enroll": "التسجيل في الدورة",
    "lessonsCount": "{count, plural, zero {لا دروس} one {درس واحد} two {درسان} few {# دروس} many {# درساً} other {# درس}}"
  }
}
```

### Множественное число — реальная ловушка

В арабском **шесть** форм: `zero`, `one`, `two`, `few` (3–10), `many` (11–99), `other`. В английском — две. Если переводчик заполняет только `one/other`, счётчики («3 урока», «11 студентов») будут звучать неграмотно на всём сайте.

CI-проверка: для локали `ar` каждый ключ с `plural` обязан содержать все шесть категорий. Отсутствие — ошибка сборки, не предупреждение.

### Проверки в CI
- Множества ключей `ar` и `en` совпадают (нет пропущенных и осиротевших).
- Совпадают наборы плейсхолдеров внутри строки (`{count}` не потерялся в переводе).
- Нет захардкоженных строк в JSX — ESLint-правило на литералы в текстовых узлах.

### Локализация серверных сообщений

Сервер **не отдаёт готовый текст для UI**. Он отдаёт стабильный код:

```json
{ "type": "…/errors/quiz-attempts-exhausted", "code": "quiz.attempts_exhausted",
  "status": 409, "meta": { "maxAttempts": 3 } }
```
Клиент переводит по `code`. Иначе перевод ошибок разъезжается между фронтом и бэком, а мобильное приложение не сможет их локализовать вообще.

Исключение — тексты, которые генерирует сервер и отправляет наружу (письма, PDF-сертификаты). Там локализация серверная, по `users.locale`, с шаблонами на обе локали.

## 3. Направление: раскладка не зеркалится

**Продуктовое решение (принято 2026-08-22):** арабская версия сохраняет раскладку
английской. Логотип слева, аккаунт справа, иллюстрация справа — позиции блоков
совпадают в обеих локалях. Справа налево читается только текст.

Это осознанное отклонение от стандарта арабских сайтов (Souq, Jarir, Namshi
зеркалят всё). Причина — единая визуальная структура для двуязычной аудитории.

### Как это реализовано

`<html dir="ltr">` в обеих локалях. Направление применяется точечно:

```css
/* Только листовые текстовые элементы. direction на flex- или grid-контейнере
   развернул бы порядок его детей — ровно то зеркалирование, которого мы избегаем. */
:root[lang="ar"] :is(h1,h2,h3,h4,h5,h6,p,blockquote,figcaption,
                     dd,dt,caption,td,th,legend,summary,label) {
  text-align: right;
}

:root[lang="ar"] :is(…):not(.tnum):not(.ltr-island) {
  direction: rtl;
}
```

Следствия, которые нужно помнить при правках:

- **Логические свойства (`ms-`, `pe-`, `text-start`) резолвятся как в английском.**
  Они больше не переключаются по локали, но остаются правильным способом писать
  отступы — просто теперь это вопрос единообразия, а не направления.
- **Выравнивание вправо задаётся вариантом `ar:`** там, где это flex-строка:
  `ar:justify-end`. Вариант объявлен как
  `@custom-variant ar (&:is(:root[lang="ar"] *))`.
- **Узкие текстовые блоки в одноколоночных секциях** получают `ar:ms-auto`,
  иначе правый край текста упирается в край блока посреди страницы. Колонки
  двухколоночных сеток не трогаем: они и так на месте.
- **Списки в контенте** помечаются классом `prose-rtl`, потому что часть `ul`
  в приложении — это flex-раскладка, и глобальное правило задело бы её.
- **Направленные иконки** зеркалятся через `:root[lang="ar"] .flip-rtl`.

### Числа ведут себя одинаково в обеих локалях

Числа, деньги и проценты форматируются **английскими конвенциями** в обеих
локалях и рендерятся в LTR-изоляции:

```css
.tnum {
  font-variant-numeric: tabular-nums;
  font-family: var(--font-mono);
  direction: ltr;
  unicode-bidi: isolate;
}
```

Без изоляции `0 / 6` показывается как `6 / 0`, а символ валюты перескакивает на
другую сторону суммы. `NUMERIC_TAG = "en-GB"` в `lib/i18n.ts` — единственное
место, где это задаётся.

Специфичность важна: правило по тегу (`:root[lang="ar"] p`) сильнее класса
`.tnum`, поэтому численные элементы явно исключены через `:not(.tnum)`.

### Что всё равно остаётся

Отказ от зеркалирования не отменяет остальные правила направления:

- **Панель управления видео — LTR.** Время течёт слева направо; зеркальный
  сикбар сбивает пользователей независимо от локали.
- **Код, URL, email, формулы, версии и телефоны** оборачиваются в `.ltr-island`
  внутри арабского текста, иначе пунктуация вокруг них прыгает.
- **Латинские вкрапления в арабской фразе** изолируются через
  `unicode-bidi: isolate`, а не переставляются руками.
- **Прогресс-бары** заполняются от начала строки: `inset-inline-start: 0` +
  `width`, не `left`.
- **Storybook и Playwright** прогоняются в обеих локалях. Половина ошибок видна
  только глазами.

## 4. Типографика

### Шрифты

Рекомендуемая пара: **IBM Plex Sans Arabic** (ar) + **IBM Plex Sans** (en) — одна метрика, единый характер, открытая лицензия.
Альтернативы: Tajawal, Almarai, Cairo (ar) + Inter (en); Noto Sans Arabic как безопасный дефолт.

Практика:
- Арабские шрифтовые файлы крупные — обязательно `woff2` + сабсеттинг под нужные unicode-диапазоны (`U+0600-06FF, U+0750-077F, U+FB50-FDFF, U+FE70-FEFF`).
- Подгружать шрифт **только текущей локали**, не оба сразу.
- `next/font/local` с `display: "swap"` и `preload` на критичном шрифте.
- Числа: если в интерфейсе смешиваются латинские и арабские цифры — задать `font-feature-settings` явно, иначе шрифт может подставить арабо-индийские глифы там, где не ждали.

### Метрики

Арабский требует **другой вертикальной ритмики**, чем латиница:

```css
html[lang="ar"] body {
  font-size: 1.0625rem;   /* ~+1px: арабский мельче читается при том же кегле */
  line-height: 1.85;      /* против 1.6 для латиницы — диакритика и выносные */
  letter-spacing: 0;      /* НИКОГДА не растягивать арабский letter-spacing'ом:
                             это разрывает связки букв и делает текст нечитаемым */
}
```

Селектор по `lang`, а не по `dir`: направление документа теперь одинаковое в
обеих локалях, различается только язык.

- `letter-spacing` на арабском — запрещено. Буквы соединяются, трекинг ломает слова визуально.
- `text-transform: uppercase` — бессмысленно (в арабском нет регистра), но применённый к смешанному тексту испортит латинские вкрапления. Не использовать глобально.
- Переносы: `hyphens` в арабском не работают; полагаться на `overflow-wrap: break-word` и достаточную ширину колонки.
- Оптимальная длина строки для арабского — 45–75 символов, как и для латиницы, но воспринимаемая плотность выше; в блоке текста давать чуть больше `max-width`.

## 5. Числа, даты, календарь

### Цифры

В Залив­е повсеместно используются **западные цифры** (0–9), а не арабо-индийские (٠–٩). Дефолт — западные. Возможность переключения — настройка профиля, не обязательный функционал.

```ts
new Intl.NumberFormat("ar-OM", { numberingSystem: "latn" }).format(1234.5)  // 1,234.5
```
Форматирование — **только через `Intl`**, никаких ручных `toFixed` + конкатенация.

### Григорианский и хиджра

Отображение даты по хиджре — ожидаемая опция для региона. Нативно, без библиотек:

```ts
new Intl.DateTimeFormat("ar-SA-u-ca-islamic-umalqura", { dateStyle: "long" }).format(d)
// ١٥ رمضان ١٤٤٧ هـ
```
В БД — **всегда `timestamptz` в UTC**. Хиджра — исключительно слой отображения. Хранить хиджра-даты в базе нельзя: конверсия неоднозначна и зависит от варианта календаря.

На бэкенде (для писем и PDF) — `hijri-converter` или `ummalqura`.

### Часовые пояса

| Страна | Зона | UTC |
|---|---|---|
| Оман, ОАЭ | Gulf Standard Time | +4 |
| КСА, Кувейт, Катар, Бахрейн | Arabia Standard Time | +3 |

Перехода на летнее время нет — одна из немногих приятных вещей. Дефолт профиля — `Asia/Muscat`, но хранить в профиле и уважать.

### Рабочая неделя

**Выходные в Омане, КСА, Катаре, Бахрейне, Кувейте — пятница и суббота.** В ОАЭ — суббота и воскресенье. Рабочая неделя начинается в воскресенье.

Это влияет на:
- drip-расписание («открывать урок каждый рабочий день»),
- дедлайны домашних заданий и их автопродление,
- расчёт «N рабочих дней на проверку»,
- дни отправки дайджестов,
- отображение календаря — первый день недели **воскресенье**, не понедельник.

Календарь выходных — конфигурация организации (`settings.weekend_days`), не хардкод.

### Рамадан и время намаза

Уведомления не отправляются:
- в тихие часы (по умолчанию 22:00–08:00 по локальному времени пользователя),
- в окна намаза (±15 мин от расчётного времени; библиотеки типа `adhan` считают по координатам).

В Рамадан — сдвиг расписания рассылок на вечер. Мелочь, которая сильно влияет на восприятие продукта локальной аудиторией. Реализуется как политика в модуле `notify`, а не как правка каждой рассылки.

## 6. Поиск на арабском

Наивный `to_tsvector('arabic', …)` работает плохо. Причины: диакритика, варианты алифа, конечная йа, та марбута, слипшиеся определённые артикли, и — главное — пользователи набирают без огласовок и без точного написания хамзы.

### Нормализация (обязательна)

```
1. Убрать татвиль (ـ U+0640)
2. Убрать харакат/огласовки (U+064B–U+0652, U+0670)
3. Алиф:        أ إ آ ٱ  →  ا
4. Йа:          ى        →  ي
5. Та марбута:  ة        →  ه
6. Хамза:       ؤ → و,  ئ → ي
7. Убрать невидимые: U+200B–U+200F, U+061C
8. Привести цифры ٠-٩ → 0-9
```

Реализация: immutable-функция в Postgres + функциональный индекс.

```sql
CREATE FUNCTION ar_normalize(t text) RETURNS text
  LANGUAGE sql IMMUTABLE PARALLEL SAFE AS $$
  SELECT regexp_replace(
           translate(t, 'أإآٱىةؤئـ٠١٢٣٤٥٦٧٨٩', 'اااايهويْ0123456789'),
           '[ً-ْٰ​-‏؜]', '', 'g')
$$;

ALTER TABLE courses ADD COLUMN search_tsv tsvector
  GENERATED ALWAYS AS (
    to_tsvector('simple', ar_normalize(coalesce(title->>'ar','') || ' ' ||
                                       coalesce(description->>'ar','')))
    || to_tsvector('english', coalesce(title->>'en','') || ' ' ||
                              coalesce(description->>'en',''))
  ) STORED;

CREATE INDEX ON courses USING gin (search_tsv);
```

Конфигурация `simple` + нормализация даёт более предсказуемый результат, чем встроенный арабский стеммер, который агрессивно режет корни. Плюс `pg_trgm` на нормализованном тексте для опечаток и подсказок.

### Когда переходить на Meilisearch

Postgres FTS хватает на каталог из сотен курсов. Как только понадобится поиск **по транскриптам видео** с ранжированием и подсветкой — переходить на Meilisearch: у него из коробки нормализация арабского, typo tolerance и приемлемое качество без настройки. Elasticsearch с `arabic` analyzer мощнее, но это отдельный сервис на 2 ГБ RAM.

### Сортировка

`ORDER BY title->>'ar' COLLATE "ar-x-icu"` — иначе арабские строки сортируются по кодам символов, что для пользователя выглядит случайным порядком.

## 7. Двуязычный контент: модель работы

### Что переводится

| Сущность | Как хранится |
|---|---|
| Короткие поля (title, subtitle, description, CTA) | JSONB `{"ar": "…", "en": "…"}` |
| Контент урока (блоки) | отдельная строка `lesson_versions` на локаль |
| Вопросы и варианты квиза | JSONB per-locale внутри `prompt` / `content` |
| Видео | **разные `media_asset`** на локаль (разная озвучка) либо один asset + дорожки субтитров |
| Сертификаты | шаблон на локаль |
| Письма | шаблон на локаль |
| Категории, теги, бейджи | JSONB per-locale |

JSONB для коротких полей выигрывает у таблицы переводов: одна строка = вся сущность, нет джойнов, легко отдать «все локали разом» в админку, индексируется выражением `((title->>'ar'))`.

### Процесс перевода

Матрица готовности в админке: строки — уроки, колонки — локали, ячейка — `missing / machine / human_review / done`.

Публикация курса на локали блокируется, если хоть один обязательный урок в статусе `missing`. Черновой машинный перевод разрешён, но помечается плашкой для студента и в отчёте для админа.

Экспорт/импорт в XLIFF или простой JSON — чтобы переводчик работал в своём инструменте, а не в нашей админке.

### Чего не делать

- **Не заводить отдельный курс на каждый язык.** Прогресс, покупка и сертификат тогда не переносятся между языками, и студент, переключивший язык, теряет всё.
- **Не машинно переводить квизы.** Формулировка вопроса — часть оценки; кривой перевод искажает статистику сложности.

## 8. PDF и генерация документов

Арабский в PDF — отдельная боль. Требуется корректный **shaping** (соединение букв) и **bidi**.

- ✅ **WeasyPrint** — использует Pango + HarfBuzz, арабский рендерится корректно из HTML/CSS. Рекомендуемый путь: HTML-шаблон сертификата → PDF.
- ✅ **Headless Chromium (Playwright)** — тоже корректно, тяжелее по ресурсам, но даёт пиксель-в-пиксель то же, что видно в браузере.
- ❌ **ReportLab** — без `arabic-reshaper` + `python-bidi` печатает разорванные, зеркальные буквы. Даже с ними качество хуже. Не использовать.

В Docker-образ воркера обязательно класть арабские шрифты (`fonts-noto-*` или свои `.ttf`), иначе PDF выйдет с «квадратиками» — классический баг, который вылезает только на проде.

Сертификат делаем **двуязычным на одном листе** (арабское имя и латинская транслитерация): его показывают и местным работодателям, и международным.

## 9. Уведомления и внешние каналы

- **Email через Resend** — единственный внешний канал: и код входа, и все уведомления. Шаблон рендерится на локали пользователя (`users.locale`).
- Код входа — самое важное письмо в системе: без него вход невозможен. SPF, DKIM и DMARC настраиваются до запуска, иначе оно уходит в спам.
- Тело письма. RTL-вёрстка письма: `dir="rtl"` на `<body>` и таблицах; почтовые клиенты плохо переваривают логические CSS-свойства, здесь как раз допустимы физические с двумя версиями шаблона.
- Тема письма и preheader — на локали пользователя; латинские названия курсов внутри арабской темы оборачивать не получится, но это допустимо.

## 10. Чек-лист «локаль готова к релизу»

- [ ] Все ключи переведены, plural-формы заполнены полностью (6 категорий для `ar`)
- [ ] Пройден Storybook в обеих локалях: позиции блоков совпадают, текст прижат вправо, направленные иконки зеркалятся
- [ ] Playwright-набор зелёный в обоих направлениях
- [ ] Шрифт локали загружается, сабсет собран, LCP в норме на 4G
- [ ] Даты, числа и валюта форматируются через `Intl`, нигде нет ручной склейки
- [ ] Любое числовое выражение несёт класс `.tnum`: `0 / 6` не превращается в `6 / 0`
- [ ] Хиджра-дата отображается там, где ожидается
- [ ] Календарь начинается с воскресенья, выходные пт–сб
- [ ] Поиск находит слова, набранные без огласовок и с разными формами алифа
- [ ] Сортировка списков по `ar-x-icu`
- [ ] PDF-сертификат рендерится с корректными связками букв
- [ ] Письма есть на обеих локалях, письмо с кодом доходит до ящика, а не в спам
- [ ] Юридические тексты (оферта, политика) переведены человеком, не машиной
