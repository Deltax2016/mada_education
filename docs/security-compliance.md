# Безопасность и защита данных

Две части: инженерная безопасность (полностью в нашей власти) и соответствие законам о персональных данных стран Залива (требует юриста, но диктует архитектурные решения).

---

## Часть I. Безопасность

### 1. Аутентификация

| Мера | Реализация |
|---|---|
| Пароли | их нет. Вход только по одноразовому коду из письма, поэтому нечего перебирать, сбрасывать и утекать |
| Access-токен | JWT 15 мин, подпись HS256 общим секретом или RS256 при появлении второго потребителя |
| Refresh-токен | 30 дней, ротация, хранится хэш; повторное использование ⇒ отзыв всего `family_id` |
| Хранение | HttpOnly + Secure + SameSite=Lax cookie; refresh с суженным `Path` |
| Код входа | 6 цифр, TTL 5 мин, хранится **хэш**, 5 попыток ввода, одноразовый |
| Лимиты | 3 отправки / 15 мин на адрес, 20 / час на IP |
| Перечисление аккаунтов | запрос кода отвечает одинаково для существующего и несуществующего адреса |
| Выход | список активных сессий, отзыв отдельной и всех сразу |
| 2FA | TOTP для ролей `admin`/`support` — обязательна, для остальных опциональна |

**Про почтовый ящик отдельно:** он становится единственным ключом к аккаунту, поэтому смена адреса подтверждается кодами на оба адреса — старый и новый. Компрометация почты означает компрометацию аккаунта; для ролей `admin` и `support` это компенсируется обязательной TOTP-двухфакторкой.

**Про доставку:** SPF, DKIM и DMARC настраиваются до запуска, иначе письма с кодом уходят в спам и вход перестаёт работать. Всплеск `auth.email_send_failed` — алерт, а не строчка в логе.

### 2. Авторизация

- Всякая проверка доступа — на API. BFF и фронт проверяют только для UX.
- Права скоуплены по курсу (`course_members`), не глобальны.
- `AccessPolicy` — единственная точка правды о доступе к контенту. Дублирование этой логики запрещено; именно там появляются дыры в платном доступе.
- IDOR: любой `GET /resource/{id}` проверяет принадлежность, а не только существование. Тест на IDOR — обязательная часть e2e-набора, а не разовая проверка.
- Impersonation: только `admin`/`support`, запись в `audit_log`, ограничение по времени, видимый баннер, запрет денежных операций и изменения доступов под чужой личиной.

### 3. Входные данные и загрузки

- Валидация всего входящего через Pydantic; неизвестные поля отклоняются (`extra="forbid"` на мутирующих схемах).
- Загрузки: белый список расширений и MIME, **проверка магических байтов после загрузки**, лимиты размера, квоты. Изображения переупаковываются (снимается EXIF и потенциальная полезная нагрузка).
- Файлы домашних заданий отдаются **только** по подписанной ссылке через проверку доступа, никогда с публичного префикса.
- Пользовательский HTML (комментарии) не хранится — только структурированные блоки, рендерятся компонентами. XSS через контент становится невозможным конструктивно.
- SQL — только через SQLAlchemy с параметрами; сырой SQL допускается в аналитике, но с биндами.
- SSRF: `embed`-блоки принимают только белый список доменов; сервер не ходит по произвольным URL от пользователя.

### 4. Транспорт и заголовки

```
Strict-Transport-Security: max-age=63072000; includeSubDomains; preload
Content-Security-Policy: default-src 'self';
  script-src 'self' 'nonce-…';
  img-src 'self' https://cdn.example data: blob:;
  media-src 'self' https://cdn.example blob:;
  connect-src 'self' https://api.example https://sentry.io;
  frame-ancestors 'none'; base-uri 'self'; object-src 'none'
Referrer-Policy: strict-origin-when-cross-origin
X-Content-Type-Options: nosniff
Permissions-Policy: camera=(), microphone=(), geolocation=()
```
CSP вводится сразу в `report-only`, через неделю — в блокирующем режиме. Позже добавить проще не получается: набегает слишком много исключений.

### 5. Секреты

- Только в переменных окружения Coolify. В репозитории — `.env.example` без значений.
- Ротация ключей платёжного провайдера и JWT-секрета — раз в год и немедленно при подозрении.
- Ключи и токены маскируются в логах (фильтр в structlog по списку полей).
- Никаких секретов в клиентском бандле: всё, что не `NEXT_PUBLIC_*`, живёт на сервере. Публикуемый ключ Thawani — единственное исключение, он и предназначен для клиента.
- Секреты Coolify выгружаются в менеджер паролей: потеря сервера без резервной копии секретов = потеря проекта.

### 6. Инфраструктура

- Postgres, Redis и MinIO **не имеют публичных портов** — только внутренняя сеть Docker.
- Контейнеры от непривилегированного пользователя, `read_only` файловая система там, где возможно, `cap_drop: ALL`.
- Базовые образы обновляются ежемесячно; `pip-audit` и `npm audit` в CI, Dependabot включён.
- SSH только по ключу, root-логин отключён, fail2ban.
- Cloudflare перед приложением: WAF, защита от ботов на `/auth/*`, rate limit на границе.

### 7. Логи и аудит

- В логи **не попадают**: коды входа, токены, полные номера карт, тела платёжных вебхуков с ПДн.
- Адреса в логах маскируются (`a***a@mada.example`).
- `audit_log` пишет: вход и выход, смена роли, выдача и отзыв доступа, изменения курса, возвраты, impersonation, экспорт данных, удаление аккаунта.
- Логи хранятся 90 дней, аудит — минимум 2 года.

### 8. Реакция на инцидент

Заранее описанный порядок (иначе в момент инцидента его придумывают на ходу):
1. Отзыв всех сессий (`revoke all`), ротация JWT-секрета.
2. Ротация ключей провайдеров и S3.
3. Фиксация состояния: снапшот БД, логи за период.
4. Оценка объёма затронутых данных по `audit_log`.
5. Уведомление регулятора и пользователей — сроки см. §11.
6. Разбор без поиска виноватых, правка процесса.

## Часть II. Персональные данные

> Ниже — инженерные требования, выведенные из законодательства региона. **Формулировки политик, оценка применимости и сроки уведомлений — к местному юристу.** Законы Залива молодые и активно меняются, а исполнительные регламенты выходят отдельно от самих законов.

### 9. Применимое право

| Юрисдикция | Акт | Что это значит практически |
|---|---|---|
| **Оман** | Закон о защите персональных данных (Королевский декрет 6/2022, в силе с 2023) + исполнительные регламенты | явное согласие на обработку, права субъекта данных, ограничения на передачу за рубеж, ответственность за нарушения; надзор — профильное министерство |
| **КСА** | PDPL (SDAIA) | требования к согласию, локализации и трансграничной передаче — жёстче оманских |
| **ОАЭ** | Федеральный декрет-закон 45/2021 | аналогичный набор прав и обязанностей |

Практический вывод: **проектировать по самому строгому из них**, а не по каждому отдельно. Дешевле один раз сделать строго, чем потом разделять поведение по странам.

### 10. Архитектурные следствия

**Согласия — доказуемые.** Таблица `consents` фиксирует: пользователь, вид согласия (`terms` / `privacy` / `marketing`), версия документа, факт выдачи или отзыва, время, IP, user-agent. Галочка в форме без записи в БД — это отсутствие доказательства.

- Согласие на маркетинг — **отдельное** от согласия с офертой, не в одном чекбоксе.
- Отзыв согласия должен быть так же прост, как выдача: одна кнопка в профиле и ссылка в каждом сообщении.
- При изменении версии политики — повторный запрос согласия, старая запись сохраняется.

**Минимизация.** Собираем только то, что нужно: адрес почты, имя, страна (для налога), локаль. Дату рождения, пол, адрес, документы — не собираем без конкретной причины. Каждое поле в `users` должно иметь ответ на вопрос «зачем оно нам».

**Права субъекта данных** — не ручная работа поддержки, а функции продукта:

| Право | Реализация | Срок |
|---|---|---|
| Доступ / переносимость | `POST /me/export` → воркер собирает JSON+файлы → ссылка на скачивание, TTL 24 ч | по закону, обычно 30 дней — делаем за минуты |
| Исправление | редактирование профиля | сразу |
| Удаление | `POST /me/delete` → подтверждение → анонимизация | 30 дней с отменой в течение 14 |
| Ограничение обработки | отключение всех каналов уведомлений | сразу |
| Возражение против маркетинга | отписка одним кликом | сразу |

**Удаление — это анонимизация, а не `DELETE`.** Финансовые записи обязаны храниться по налоговому законодательству, а результаты обучения нужны для статистики курса. Порядок:

```
users:            phone/email/имена/аватар → null, status='deleted',
                  добавляется anonymized_at
orders/invoices:  сохраняются (налоговое требование), user_id остаётся,
                  но персональные данные уже удалены из users
learning_events:  user_id заменяется на псевдоним, если данные нужны для агрегатов
comments:         автор → «удалённый пользователь», содержимое по политике
media (домашние): удаляются физически
certificates:     сохраняются (публичная верификация), имя остаётся —
                  это осознанное исключение, о нём предупреждаем при удалении
```

Что удаляется, а что нет — прописывается в политике конфиденциальности **до запуска**, а не после первого запроса.

**Трансграничная передача.** Хостинг за пределами страны субъекта данных и передача данных подрядчикам (Cloudflare, Sentry, Resend, платёжный провайдер) — это трансграничная передача. Требования различаются по странам и могут включать согласие субъекта, договорные гарантии или уведомление регулятора.

Практически:
- вести **реестр субпроцессоров**: кто, какие данные, где хранит, на каком основании;
- заключить DPA с каждым;
- перечислить их в политике конфиденциальности;
- решение о регионе хостинга принимать с учётом этого — см. [deploy-coolify.md](deploy-coolify.md) §1. Если появятся государственные или крупные корпоративные клиенты в Омане, требование локального хранения возникнет почти наверняка; вся система в docker-compose именно поэтому — переезд остаётся выполнимым.

**Сроки хранения.** Не «храним вечно»:

| Данные | Срок |
|---|---|
| Аккаунт и прогресс | пока активен + 3 года неактивности, затем уведомление и анонимизация |
| Финансовые документы | по налоговому законодательству (обычно ~10 лет) |
| Логи приложения | 90 дней |
| Аудит-лог | 2 года минимум |
| Файлы домашних заданий | 1 год после завершения курса |
| OTP, токены сессий | до истечения + 30 дней |
| Аналитические события | 2 года в сыром виде, далее только агрегаты |

Реализуется задачами по расписанию, а не «когда вспомним».

**Уведомление об утечке.** Порядок и сроки уведомления регулятора и пользователей различаются по странам и обычно измеряются днями. Готовые шаблоны уведомлений (на ar и en) должны лежать заранее — искать формулировки в момент инцидента поздно.

**Дети.** Если платформа доступна лицам младше 18, потребуется согласие опекуна. Проще и безопаснее — ограничить регистрацию возрастом и явно указать это в оферте, пока не появится продуманный сценарий для несовершеннолетних.

### 11. Документы, нужные к запуску

Все — на арабском и английском, переведённые человеком (машинный перевод юридического текста — источник проблем):

- [ ] Политика конфиденциальности (с перечнем субпроцессоров и сроков хранения)
- [ ] Пользовательское соглашение / оферта
- [ ] Политика возвратов
- [ ] Политика cookie + баннер согласия (по умолчанию всё необязательное **выключено**)
- [ ] Согласие на маркетинговые рассылки — отдельным чекбоксом
- [ ] Реестр обработки и субпроцессоров (внутренний документ)
- [ ] Контакт для запросов по персональным данным

## 12. Чек-лист перед запуском

**Безопасность**
- [ ] Аутентификация: ротация refresh, отзыв семейства, лимиты на код проверены нагрузочно
- [ ] Запрос кода не различает существующий и несуществующий адрес
- [ ] Тесты на IDOR по всем ресурсам с `{id}` в пути
- [ ] `AccessPolicy` покрыта тестами на все шесть исходов
- [ ] `is_correct` не утекает в API во время попытки (тест на сериализацию)
- [ ] Платное видео недоступно без `/playback`
- [ ] CSP в блокирующем режиме, HSTS включён
- [ ] Внутренние сервисы без публичных портов
- [ ] Секреты только в Coolify, выгружены в менеджер паролей
- [ ] Логи не содержат ПДн и токенов
- [ ] Порядок реакции на инцидент записан и известен команде

**Данные**
- [ ] Записи согласий пишутся с версией документа
- [ ] Экспорт данных работает и отдаёт всё
- [ ] Удаление аккаунта анонимизирует по описанной схеме
- [ ] Задачи очистки по срокам хранения запущены
- [ ] Реестр субпроцессоров заполнен, DPA подписаны
- [ ] Юридические документы опубликованы на ar и en
- [ ] Отписка от рассылок работает в один клик из каждого сообщения
