# Платежи: Thawani и рынок Залива

---

## 1. Три вещи, которые ломают наивную реализацию

1. **OMR — трёхзнаковая валюта.** 1 риал = 1000 байса. KWD и BHD тоже. Любой код с `amount / 100`, `Decimal(amount).quantize(Decimal("0.01"))` или `toFixed(2)` даёт неверную сумму. Thawani принимает суммы **в байсах целым числом** — это не особенность API, это устройство валюты.

2. **Локальные платёжные схемы обязательны.** У существенной доли клиентов в регионе нет карты, работающей с международными эквайерами: в Омане это OmanNet-дебет, в КСА — mada, в Кувейте — KNET, в Бахрейне — Benefit. Провайдер без поддержки местной схемы отсекает часть покупателей ещё до формы оплаты.

3. **Возврат пользователя на `success_url` не является подтверждением оплаты.** Вкладку закрывают, интернет рвётся, URL подделывают. Единственный авторитетный источник — серверный запрос статуса у провайдера.

## 2. Абстракция провайдера

```python
class PaymentProvider(Protocol):
    name: str
    supported_countries: set[str]
    supported_currencies: set[str]

    async def create_checkout(self, order: Order, user: User) -> CheckoutSession
    async def fetch_status(self, order: Order) -> PaymentStatus       # ← авторитетный источник
    async def parse_webhook(self, headers: Mapping, body: bytes) -> WebhookEvent | None
    async def refund(self, order: Order, amount: Money, reason: str) -> RefundResult
```

Выбор провайдера — по стране пользователя и валюте заказа, с приоритетами и fallback'ом:

```
OM              → Thawani            → PayTabs (резерв)
SA, AE, KW, BH, QA → PayTabs / Tap    → Stripe
прочие           → Stripe
```

Провайдер записывается в `orders.provider` при создании заказа и **не меняется** — иначе сверка и возвраты уйдут не туда.

## 3. Thawani — основной провайдер для Омана

Лицензированный Центральным банком Омана платёжный шлюз. Поддерживает OmanNet-дебет, международные карты, кошелёк Thawani, Apple Pay.

> Точные поля, лимиты сумм и наличие вебхуков сверять с актуальной документацией Thawani при онбординге — API развивается. Схема ниже описывает интеграцию так, чтобы она была корректна независимо от того, есть вебхуки или нет.

### Окружения

```
UAT:  https://uatcheckout.thawani.om/api/v1
PROD: https://checkout.thawani.om/api/v1
Заголовок аутентификации: thawani-api-key: <secret_key>
Публикуемый ключ используется в URL страницы оплаты.
```

Наличие UAT — важно: сквозной тест оплаты попадает в CI и в e2e-набор.

### Создание сессии

```http
POST /checkout/session
thawani-api-key: <secret>

{
  "client_reference_id": "<order.id>",
  "mode": "payment",
  "products": [
    { "name": "Course: Financial Literacy", "quantity": 1, "unit_amount": 12500 }
  ],
  "success_url": "https://app.example/ar/checkout/return?order=<order.id>",
  "cancel_url":  "https://app.example/ar/checkout/cancel?order=<order.id>",
  "metadata": { "orderId": "<order.id>", "userId": "<user.id>", "locale": "ar" }
}
```

- `unit_amount` — **в байсах**: `12500` = 12.500 OMR.
- `client_reference_id = order.id` — даёт естественную идемпотентность и позволяет искать сессию по нашему id.
- `name` продукта уходит в SMS/чек клиента — писать понятно, учитывать длину, для арабской аудитории имеет смысл дублировать название на арабском.
- В `metadata` не класть персональные данные сверх необходимого.

Ответ содержит `session_id`. Пользователь редиректится на страницу оплаты Thawani:

```
https://checkout.thawani.om/pay/{session_id}?key={publishable_key}
```

### Проверка статуса — авторитетный путь

```http
GET /checkout/session/{session_id}
GET /checkout/reference/{client_reference_id}
```

`payment_status` ∈ `unpaid` | `paid` | `cancelled`.

**Только этот ответ меняет статус заказа.** Ни `success_url`, ни данные из query-параметров, ни сообщение пользователя «я оплатил».

### Сохранённые карты и повторные списания

Для подписок и оплаты в один клик у Thawani есть Customer API (`customer_id`) и Payment Intent. Подключать только когда появятся подписки — для разовых покупок это лишняя сложность и лишние ПДн.

### Возвраты

Возможность и порядок возвратов зависят от соглашения с Thawani. Уточнить на онбординге. До подтверждения — считать, что возврат делается вручную через кабинет мерчанта, а в системе фиксируется запись в `refunds` со статусом `manual`.

### Онбординг — на критическом пути

Требуется оманская компания (CR), банковский счёт, комплаенс-проверка. Это **недели**, а не дни. Начинать одновременно с Фазой 0, до того как код оплаты понадобится. Пока идёт онбординг — разработка на UAT.

## 4. Поток оплаты целиком

```
 [1] POST /billing/orders          Idempotency-Key обязателен
     расчёт: цена + промокод − скидка + НДС по стране
     order.status = pending, expires_at = now + 30 мин
              │
 [2] POST /billing/orders/{id}/checkout
     provider.create_checkout() → session_id
     сохраняем provider_session_id, отдаём redirectUrl
              │
 [3] Редирект на страницу Thawani ─────────────────┐
              │                                     │
 [4] Пользователь вернулся на /checkout/return      │  или НЕ вернулся
     Фронт НЕ верит URL. Начинает поллить           │  (закрыл вкладку,
     GET /billing/orders/{id} раз в 2 с, до 60 с    │   потерял сеть)
              │                                     │
 [5] Первый же поллинг триггерит на сервере         │
     provider.fetch_status() (не чаще 1 раза в 2 с) │
              │                                     │
 [6] paid → транзакция:                             │
       order.status = paid, paid_at                 │
       создать enrollment                           │
       записать в outbox: order.paid                │
       сгенерировать номер инвойса                  │
              │                                     │
 [7] Воркер outbox: письмо «доступ открыт»           │
              │                                     │
 [8] Воркер сверки (каждые 5 мин) ◄─────────────────┘
     выбирает orders where status='pending'
       and created_at < now() - 3 min
       and check_attempts < 20
     → fetch_status() → paid | cancelled | оставить pending
     → по истечении expires_at → status = expired
```

Шаг [8] — **не подстраховка, а основной путь** для всех, кто не вернулся на сайт. Без него часть оплативших клиентов не получит доступ, и это выяснится через обращения в поддержку.

```sql
-- индекс, на котором держится вся сверка
create index on orders (status, last_checked_at) where status = 'pending';
```

### Идемпотентность

- `orders.idempotency_key` unique — повтор `POST /orders` с тем же ключом возвращает существующий заказ.
- `client_reference_id` = `order.id` — Thawani не создаст дубль по нашей вине.
- Обработка `paid` обёрнута в транзакцию с проверкой `status = 'pending'`: гонка «вебхук + поллинг + возврат пользователя» одновременно не создаст два enrollment'а.
- Все входящие события пишутся в `payment_events` с `unique(provider, external_id, kind)` — повторная доставка не обрабатывается дважды.

### Вебхуки, если они есть

Обработчик: проверить подпись → записать в `payment_events` → **ответить 200 немедленно** → обработать асинхронно. Долгая обработка внутри вебхука приводит к таймаутам и лавине ретраев. Вебхук — оптимизация скорости, поллинг — гарантия.

| Провайдер | Покрытие | Локальные схемы | Когда брать |

## 6. Деньги в коде

```python
@dataclass(frozen=True)
class Money:
    minor: int          # 12500
    currency: str       # "OMR"

    @property
    def exponent(self) -> int:      # из справочника currencies, НЕ константа 2
        return CURRENCY_EXPONENT[self.currency]

    def format(self, locale: str) -> str:
        return Intl.number(self.minor / 10 ** self.exponent, locale, self.currency)
```

Правила:
- В БД — `bigint minor` + `char(3) currency`. Никогда `float`, никогда `numeric` для сумм в API.
- В API — объект `{ minor, currency, exponent, display }`, не число.
- Арифметика — только над `minor` в целых числах.
- Округление НДС — на уровне заказа, не построчно, и по правилам страны.
- Мультивалютных заказов не существует: один заказ — одна валюта.
- Литерал `100` рядом с деньгами — красный флаг на ревью.

## 7. НДС и налоги

Ставки на момент написания (**подлежат проверке у налогового консультанта — они меняются**):

| Страна | Стандартная ставка НДС |
|---|---|
| Оман | 5 % |
| ОАЭ | 5 % |
| КСА | 15 % |
| Бахрейн | 10 % |
| Катар | нет |
| Кувейт | нет |

Хранятся в таблице `tax_rates` с интервалами дат, не в коде.

### Вопрос, который нужно закрыть до запуска продаж

**Облагаются ли онлайн-курсы НДС в Омане, и есть ли освобождение для образовательных услуг?**

В ряде стран Залива образовательные услуги освобождены или облагаются по нулевой ставке, но освобождение обычно распространяется только на **лицензированные образовательные учреждения**, а коммерческие онлайн-курсы под него часто не подпадают. Ответ напрямую влияет на цену, которую видит покупатель, и на обязанность регистрироваться по НДС.

Это вопрос к местному налоговому консультанту, а не к архитектуре. Но архитектура должна быть готова к любому ответу:

- `products.tax_mode` = `inclusive` | `exclusive` — в рознице региона привычнее показывать цену **с включённым налогом**;
- ставка определяется по `orders.tax_country` (страна покупателя), фиксируется в заказе на момент покупки и не пересчитывается задним числом;
- при трансграничных продажах (покупатель из КСА, продавец из Омана) применяются правила места оказания услуг — тоже вопрос к консультанту;
- порог обязательной регистрации по НДС в Омане низкий; при выходе на него нужна регистрация.

### Инвойсы и e-invoicing

- Каждый оплаченный заказ порождает `invoice` с последовательным номером и PDF — двуязычный, с реквизитами продавца, VAT-номером, ставкой и суммой налога.
- Номера — строго последовательные, без пропусков, генерируются из отдельной последовательности БД (не из `count(*)`).
- В КСА действует обязательное e-invoicing (ZATCA/Fatoora) со структурированным форматом и QR-кодом — актуально, если появится саудовское юрлицо. В Омане введение e-invoicing анонсировано; следить за сроками.
- Хранить инвойсы минимум столько, сколько требует местное налоговое законодательство (обычно 10 лет) — учесть в политике хранения данных.

## 8. Промокоды, возвраты, доступ

**Промокоды:** процент или фиксированная сумма (в minor units и валюте), привязка к продуктам, срок, общий лимит и лимит на пользователя, счётчик через `promo_redemptions` с уникальным индексом. Проверка и списание — в одной транзакции с созданием заказа, иначе код «размножается» при параллельных запросах.

**Возвраты:** политика («14 дней и не более 20 % пройденного курса») реализуется в сервисе, а не в переписке с поддержкой. Возврат → `refunds` → отзыв `enrollment` (`status = revoked`) → уведомление. Частичный возврат при частичном прохождении — считается от доли пройденных обязательных уроков.

**Срок доступа:** `products.access_days` → `enrollments.access_ends_at`. За 7 дней до истечения — уведомление с предложением продлить. Истёкший доступ **не удаляет прогресс**: при повторной покупке студент продолжает с того же места. Это заметно влияет на возвраты покупателей.

## 9. B2B

Отдельный поток, не «много разовых покупок»:
- заявка → счёт (`proforma invoice`) → банковский перевод → ручное подтверждение → выдача N мест;
- `b2b_accounts` / `b2b_seats`, приглашения сотрудников по номеру телефона или CSV;
- отчёт по прогрессу сотрудников для менеджера компании;
- корпоративные закупки в регионе часто идут через тендеры и по счёту — карточная оплата тут не работает.

## 10. Замечание по названию

**mada** (مدى) — название национальной платёжной схемы Саудовской Аравии; это зарегистрированная марка. Слово также означает «предел, охват» по-арабски, и совпадение может быть случайным.

Практическое следствие: если планируется выход на саудовский рынок, стоит заранее проверить название на конфликт с товарным знаком и учесть, что в платёжном контексте «mada» у местной аудитории однозначно ассоциируется с картами. Это вопрос к юристу по IP на раннем этапе — переименование после запуска обходится дорого.

## 11. Чек-лист готовности биллинга

- [ ] Суммы — целые minor units, exponent из справочника; тест на OMR с тремя знаками
- [ ] Онбординг Thawani запущен, UAT-ключи получены
- [ ] Сквозной тест оплаты в UAT прогоняется в CI
- [ ] `success_url` не меняет статус заказа (тест: подделанный возврат не даёт доступ)
- [ ] Воркер сверки закрывает заказ, если пользователь не вернулся (тест: закрытая вкладка)
- [ ] Повторная доставка события не создаёт второй enrollment
- [ ] Промокод не «размножается» при параллельных запросах
- [ ] Инвойс генерируется, номера последовательны, PDF двуязычный и корректно рендерит арабский
- [ ] Ставка НДС фиксируется в заказе, вопрос об освобождении для образования закрыт письменно
- [ ] Возврат отзывает доступ, но не стирает прогресс
- [ ] Ключи провайдера только в секретах Coolify, в логах маскируются
